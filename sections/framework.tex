\section{vLLM-FI Framework}
\label{sec:framework}

vLLM-FI extends the vLLM inference engine with runtime fault injection and reliability evaluation, reusing its native model execution and distributed runtime. First, we extend fault models for distributed LLM inference to account for computational workload and inter-device communication, enabling analysis of how faults affect inference outputs and downstream-task performance under different execution configurations. Second, we integrate fault configuration and target selection into vLLM's multi-process execution path to coordinate injection across distributed Workers and apply faults to the intended runtime tensors. Third, we implement GPU-resident, in-place bit-flip operators to reduce data transfers and injection overhead in large-scale fault-injection campaigns. The following subsections detail the system architecture, fault models, injection and evaluation workflow, and GPU implementation.

\subsection{System Architecture}
\label{subsec:architecture}

vLLM improves inference throughput and GPU memory utilization through continuous batching, PagedAttention-based KV-cache management, optimized computation kernels, quantized model execution, and distributed parallelism \cite{kwon2023efficient}. These capabilities make vLLM a suitable foundation for evaluating the reliability of practical LLM inference systems. However, they also make conventional model-level fault injection difficult to apply directly. A model may be partitioned differently according to the selected parallel strategy, and multiple parallel ranks are executed in separate Worker processes. Consequently, the model layers, parameters, intermediate results, and communication buffers to be injected are distributed across multiple devices and processes.

Figure~\ref{fig:vllmfi_architecture}(a) presents the overall vLLM-FI workflow, from fault configuration and task inputs through the vLLM-FI executor to evaluation. The input stage specifies the fault type, mode, target layer, and rank together with the model, parallelism, and inference settings. The executor integrates FaultConfig with the native vLLM configuration and propagates it to the distributed Workers, while vLLM schedules task requests for token-level execution on the corresponding model partitions. The evaluation stage passes the resulting model outputs to lm-evaluation-harness \cite{eval-harness} for task-specific scoring, connecting configurable injection with downstream reliability assessment.

Figure~\ref{fig:vllmfi_architecture}(b) shows where the configured faults are applied within a Worker's model computation. The illustrated injector maps each configuration to a target in the attention or MLP block: a memory fault modifies the QKV projection weights, a compute fault perturbs an attention-computation result, and a communication fault modifies the output buffer associated with the MLP down projection before inter-device exchange. These examples connect the experiment-level settings in Fig.~\ref{fig:vllmfi_architecture}(a) to concrete injection locations in Fig.~\ref{fig:vllmfi_architecture}(b). At each selected location, the fault model determines the number of events, and the CUDA backend performs in-place bit flips on the GPU-resident tensor.

\subsection{Extended Fault Models}
\label{subsec:fault_models}

vLLM-FI supports memory, compute, and communication faults. In this work, these models target model weights, matrix-computation outputs, and software-visible communication buffers, respectively. As illustrated in Fig.~\ref{fig:three_fault_models}, injected weight corruption persists after loading, a compute fault perturbs an intermediate result during inference, and a communication fault affects data transferred between devices.

For each fault model, vLLM-FI provides both fixed-count and bit-error-rate modes. Fixed-count mode directly specifies the number of fault events. In bit-error-rate mode, the number of fault events is sampled from a Poisson distribution whose parameter is determined by the exposure associated with the selected fault model.

\subsubsection{Memory Faults}

Memory faults can corrupt data stored during LLM inference, including model weights, activations, and the KV cache. This work focuses on model weights because their long lifetime and repeated reuse allow corruption to affect many subsequent forward computations and decoding steps. A corrupted weight can therefore introduce persistent perturbations into inference and degrade downstream-task performance.

To evaluate this effect, vLLM-FI applies configurable bit flips to selected weight tensors as they are loaded into GPU memory. The modified values are retained and used in subsequent inference, allowing the evaluation workflow to measure their impact on model outputs. The loading stage serves as the injection point for establishing persistent weight corruption; the model does not restrict the physical occurrence of memory faults to model loading.

To determine the injection count, consider a weight tensor $\mathbf{W}$ containing $|\mathbf{W}|$ elements, each with a storage width of $b$ bits. Let $\rho_{\mathrm{mem}}$ denote the effective fault-event rate per stored bit over the modeled injection exposure, rather than a rate per unit time. The expected number of memory fault events and the corresponding fault-count distribution are modeled as
\begin{align}
    \lambda_{\mathrm{mem}}
    &= |\mathbf{W}|b\rho_{\mathrm{mem}},
    \label{eq:memory_exposure}\\
    N_{\mathrm{faults}}^{\mathrm{mem}}
    &\sim \operatorname{Poisson}(\lambda_{\mathrm{mem}}).
    \label{eq:memory_poisson}
\end{align}

\subsubsection{Compute Faults}

Compute faults model the effect of transient errors in arithmetic units on intermediate computation results \cite{ashraf2015understanding}. Existing model-level fault injection methods commonly estimate the number of compute faults according to the number of elements in an output tensor. However, the output size does not necessarily reflect the amount of computation required to produce that output.

For example, multiplying matrices with shapes $(a_1,a_2)$ and $(a_2,a_1)$ produces an output containing $a_1^2$ elements, but requires $a_1^2a_2$ multiply--accumulate operations. Increasing $a_2$ therefore increases the computational fault exposure without changing the number of output elements. This difference becomes more important for LLMs because of their large projection dimensions and the repeated execution of matrix operations during autoregressive decoding.

Following prior LLM reliability studies \cite{sun2025demystifying,sun2025ft2,xie2025realm}, vLLM-FI injects compute faults into the outputs of GEMM and related matrix operations. However, the number of faults is determined by the estimated multiply--accumulate workload rather than solely by the output-tensor size. Let $\mathcal{C}_{\mathrm{total}}$ be the estimated number of executed MAC operations and $b_{\mathrm{inj}}$ be the data width at the injection point. The bit-width-weighted MAC exposure proxy, expected fault count, and fault-count distribution are modeled as follows:
\begin{align}
    \mathcal{E}_{\mathrm{comp}}
    &= \mathcal{C}_{\mathrm{total}}b_{\mathrm{inj}},
    \label{eq:compute_exposure}\\
    \lambda_{\mathrm{comp}}
    &= \rho_{\mathrm{comp}}\mathcal{E}_{\mathrm{comp}},
    \label{eq:compute_lambda}\\
    N_{\mathrm{faults}}^{\mathrm{comp}}
    &\sim \operatorname{Poisson}(\lambda_{\mathrm{comp}}),
    \label{eq:compute_poisson}
\end{align}
where $\rho_{\mathrm{comp}}$ denotes the effective fault-event rate per bit-width-weighted MAC operation. The exposure is a model-level proxy and does not represent an exact count of physical bit-level operations inside the GPU.

Algorithm~\ref{alg:mac_estimation} summarizes the runtime MAC estimation procedure. Linear projections use their executed batch size, input dimension, and output dimension. Fused modules, such as gate\_up\_proj, are treated according to the dimensions of the fused runtime operator. Attention computation is estimated using the sequence metadata provided by vLLM, allowing the framework to distinguish prefill from decode and to account for the effective number of query--key pairs under causal attention.

\subsubsection{Communication Faults}

Communication faults model errors affecting data exchanged between devices during distributed inference. vLLM-FI targets software-visible communication buffers in both tensor-parallel and pipeline-parallel execution. For tensor parallelism, faults are injected into buffers associated with collective operations such as All-Reduce. For pipeline parallelism, faults are injected into activation buffers transferred between adjacent pipeline stages.

At a selected communication location, let $\mathbf{B}$ denote the communication buffer, $|\mathbf{B}|$ the number of elements in that buffer, $b$ the number of bits per element, and $\rho_{\mathrm{comm}}$ the effective fault-event rate per buffer bit for the modeled injection exposure. The expected event count and corresponding distribution are

\begin{align}
    \lambda_{\mathrm{comm}}
    &= |\mathbf{B}|b\rho_{\mathrm{comm}},
    \label{eq:comm_exposure}\\
    N_{\mathrm{faults}}^{\mathrm{comm}}
    &\sim \operatorname{Poisson}(\lambda_{\mathrm{comm}}).
    \label{eq:comm_poisson}
\end{align}

The selected bits are modified before the corresponding collective operation or pipeline-stage transfer. The corrupted buffer therefore participates in subsequent communication and computation, allowing the resulting error to propagate across devices.


\subsection{vLLM-Native Fault Injection and Evaluation}
\label{subsec:runtime_injection}

A fault configuration must reach the injection sites executed by distributed vLLM Workers. vLLM-FI embeds FaultConfig in VllmConfig and uses vLLM's existing propagation path through the Engine, Executor, Worker, and ModelRunner. Each Worker consults the configuration at its local injection sites and uses its rank, pipeline stage, and target information to determine whether a fault applies. This avoids a separate cross-process control channel.

Weight faults are injected during the weight-loading methods of vLLM's linear layers, where both the layer identifier and the parameter being loaded are available. The injector receives the tensor held by the local Worker: under tensor parallelism (TP) \cite{shoeybi2019megatron}, this is the local weight shard; under pipeline parallelism (PP) \cite{huang2019gpipe}, only the stage owning the layer reaches its loading site. For quantized weights, target selection also uses the stored parameter name. In the supported paths, GPTQ and AWQ target packed qweight parameters, whereas FP8 targets weight parameters.

Compute and communication faults are injected in the corresponding forward paths. Compute injection modifies the output of a selected matrix operation after it is produced. Communication injection modifies the buffer associated with a TP collective or PP stage transfer. Locating these hooks in shared runtime layers allows the injection logic to be reused across supported model implementations.

Algorithm~\ref{alg:vllmfi-injection} describes the procedure at a candidate site reached by a Worker. The event type determines the local tensor and its exposure. A Poisson draw gives the number of candidate fault events, which are applied when the configured rank and target selectors match.

\begin{algorithm}[t]
\footnotesize
\DontPrintSemicolon
\SetAlgoVlined
\SetInd{0.35em}{0.75em}
\SetAlgoNlRelativeSize{-1}

\caption{Fault Injection in vLLM-FI}
\label{alg:vllmfi-injection}

\KwIn{Fault configuration $F$ with error rate $r$; Worker $w$}
\KwOut{Local tensors modified at eligible injection sites}

\ForEach{candidate event $e$ reached by Worker $w$}{
    \If{$\neg\operatorname{PatternEnabled}(F,e)$}{
        \textbf{continue}\;
    }

    \If{$e=\mathrm{WeightLoad}$}{
        $T\leftarrow\operatorname{LocalParameter}(w,e)$\;
        $S\leftarrow|T|$\;
    }
    \If{$e=\mathrm{ComputeOutput}$}{
        $T\leftarrow\operatorname{Output}(e)$\;
        $S\leftarrow N_{\mathrm{MAC}}(e)$\;
    }
    \If{$e\in\{\mathrm{TPComm},\mathrm{PPComm}\}$}{
        $T\leftarrow\operatorname{Buffer}(e)$\;
        $S\leftarrow N_{\mathrm{comm}}(e)$\;
    }

    $n\sim\operatorname{Poisson}\!\left(S\,b(T)\,r\right)$\;
    \If{$n>0$ and $\operatorname{RankMatch}(F,w,e)$ and
        $\operatorname{TargetMatch}(F,e,T)$}{
        $m_e\leftarrow\operatorname{Mode}(F,e)$\;
        $T\leftarrow\operatorname{BitFlip}(T,n,m_e)$\;
    }
}
\end{algorithm}

Here, $\operatorname{PatternEnabled}$ checks whether the configured fault type corresponds to the candidate site. $\operatorname{RankMatch}$ checks the relevant TP rank or PP stage, while $\operatorname{TargetMatch}$ checks the layer, module, and, where applicable, the parameter name. The exposure $S$ is the local parameter element count, the number of multiply--accumulate operations, or the communication exposure count. The function $b(T)$ gives the storage bit width used for sampling. The sampled value $n$ counts candidate fault events; the selected mode $m_e$ determines how many bit positions each event changes.

For task-level reliability evaluation, vLLM-FI adapts lm-evaluation-harness to pass FaultConfig alongside the existing vLLM parameters. The harness prepares benchmark inputs, runs inference under the specified fault configuration, collects fault-affected outputs, and computes the selected task's native metrics. This connects Worker-local injection with standardized downstream evaluation.

\subsection{GPU-Resident In-Place Bit-Flip Operator}
\label{subsec:cuda_operator}

PyTorch-level fault-injection tools for CNNs and conventional DNNs
emphasize portability and extensibility
\cite{mahmoud2020pytorchfi,huang2024mrfi}. In LLM decoding, injection sites are encountered repeatedly, while the expected number of fault events grows with compute exposure and the configured error rate.These properties can increase the runtime cost of CPU-assisted tensor modification. To limit this overhead, vLLM-FI batches bit flips in a
GPU-resident, in-place operator. We evaluate the runtime impact of this design in the subsequent experiments.

Algorithm~\ref{alg:cuda_bitflip} summarizes the update for a contiguous GPU tensor $\mathbf{X}$ and $N$ fault events. The packed-word path requires a 32-bit-aligned base and accessible enclosing words. The operator assigns one CUDA thread to each event on the current stream. Each thread samples an element and bit positions, constructs a mask, and atomically XORs the corresponding storage. The input tensor is modified without a CPU copy.

\begin{algorithm}[t]
\footnotesize
\DontPrintSemicolon
\SetAlgoVlined
\SetInd{0.35em}{0.75em}
\SetAlgoNlRelativeSize{-1}

\caption{GPU In-Place Bit-Flip Injection}
\label{alg:cuda_bitflip}

\KwIn{Contiguous GPU tensor $\mathbf{X}$ with base aligned to $\max(32,w_d)$ bits and accessible enclosing words;
fault count $N$; data type $d$ with $w_d\in\{8,16,32,64\}$;
bit policy $f\in\{\mathrm{S},\mathrm{E},\mathrm{M},\mathrm{ALL}\}$; bits per event $k\in\{1,2\}$; random seed $s$}
\KwOut{Modified tensor $\mathbf{X}$}

$\mathcal{B}\leftarrow\mathcal{B}_{f}(d)$\;

\tcp{Each iteration is executed by one CUDA thread}
\For{$i\leftarrow 0$ \KwTo $N-1$}{
    Initialize thread-local RNG using $s$ and $i$\;
    $j_i\leftarrow\operatorname{RandomIndex}(|\mathbf{X}|)$\;
    Select $k$ bit positions $p_{i,r}\in\mathcal{B}$\;

    \If{$k=2$ and $|\mathcal{B}|>1$}{
        Resample duplicate positions up to the retry limit\;
    }

    $m\leftarrow 0$\;
    \For{$r\leftarrow 1$ \KwTo $k$}{
        $m\leftarrow m\mathbin{\mathrm{OR}}(1\ll p_{i,r})$\;
    }

    \eIf{$w_d\in\{8,16\}$}{
        $q\leftarrow\lfloor j_i/(32/w_d)\rfloor$\;
        $\delta\leftarrow w_d(j_i\bmod(32/w_d))$\;
        $\operatorname{atomicXor}_{32}
        (\mathbf{X}_{32}[q],m\ll\delta)$\;
    }{
        $\operatorname{atomicXor}_{w_d}
        (\mathbf{X}_{w_d}[j_i],m)$\;
    }
}
\end{algorithm}

Bit positions are numbered from the least significant bit, and $\mathcal{B}_{\mathrm{ALL}}(d)=\{0,\ldots,w_d-1\}$. For FP16, the sign, exponent, and mantissa occupy bits $\{15\}$, $\{10,\ldots,14\}$, and $\{0,\ldots,9\}$; for BF16, they occupy $\{15\}$, $\{7,\ldots,14\}$, and $\{0,\ldots,6\}$. The corresponding sets are $\{7\}$, $\{2,\ldots,6\}$, and $\{0,1\}$ for FP8 E5M2, and $\{7\}$, $\{3,\ldots,6\}$, and $\{0,1,2\}$ for FP8 E4M3FN. For integer types, the policies select the most significant bit or predefined high- and low-order ranges. In two-bit mode, a sign-only selection yields one effective flip; a duplicate remaining after the bounded retries does likewise.

The unsigned views $\mathbf{X}_{32}$ and $\mathbf{X}_{w_d}$ in Algorithm~\ref{alg:cuda_bitflip} refer to the same tensor storage. CUDA provides atomic XOR for 32-bit and 64-bit words, so the operator places 8-bit and 16-bit masks in their enclosing 32-bit word. This packed-word mapping assumes a 32-bit-aligned base, accessible enclosing words, and little-endian lane order. The shifted mask changes only the selected lane, while atomic updates preserve concurrent toggles to the same word. Repeated toggles of one bit follow XOR parity: an even number restores its original value.

Type-specific dispatch supports FP64, FP32, FP16, BF16, INT8, UINT8, INT16, INT32, INT64, FP8 E5M2, and FP8 E4M3FN.
